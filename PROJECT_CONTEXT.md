# Georgian Property Intelligence Platform

## Project goal

Build a Georgian real estate decision-support platform. Help users compare properties and understand asking prices, rather than simply browse listings.

## Current setup

- Solo founder using Claude Free.
- Budget: $0 until launch.
- Windows, Next.js, TypeScript, Tailwind CSS.
- Local development only.
- Demo data only. Every demo listing must be clearly labeled.
- Never present demo data as real.
- No scraping and no AI features in the MVP.

## Stack plan

- Next.js App Router + TypeScript
- Tailwind CSS and shadcn/ui
- Georgian and English languages first; Russian later
- PostgreSQL (hosted later, e.g. Supabase; nothing provisioned yet) for data, authentication and storage when needed
- Since Step 1.19: hand-written SQL migrations + `pg` (node-postgres) on the server; PGlite (PostgreSQL in WebAssembly) for integration tests. Drizzle ORM was evaluated and not adopted for now (see `db/README.md`). Zod when needed; Vitest. Maps: Leaflet 1.9.4 (BSD-2-Clause) since Step 1.13, used directly without a React wrapper.

## Architecture rules

- Keep business logic separate from UI components.
- Separate physical properties from listings/offers and listing history.
- Support USD and GEL.
- Market comparisons must refer to asking prices of similar active listings, never claim to be verified transaction prices or definitive fair value.
- Validate user input.
- Never expose secrets in client-side code.
- Add dependencies only when needed.
- Do not implement scraping or real-data ingestion without a separate review.

## Folder conventions

- `app/` holds routes and pages only (the project has no `src/` folder).
- `lib/` holds business logic, split by topic (for example `lib/pricing/`, `lib/currency/`, `lib/analytics/`, `lib/db/`, `lib/repository/`). Files in `lib/` must be plain TypeScript: no React, no imports from `app/` or `components/`. The exceptions are `lib/currency/get-exchange-rate.ts` and `lib/data/listings.ts` (server-only), which use `next/cache` (`"use cache"`, `cacheLife`) to wrap plain, tested logic. Pages read listings only through `lib/data/listings.ts` (repository), never from the demo arrays; `lib/db/` is server-only and never imported by client components.
- `components/` holds UI components, split by topic: `components/site/` (header, footer, logo), `components/properties/` (cards, filters, demo labels, illustration, facts, price per m², asking-price context), `components/currency/` (currency toggle, rate notice, display-currency hook and switch), `components/compare/` (compare button, tray, comparison table, header link), `components/storage/` (browser store helper), `components/favorites/` (heart button, favorites hook, favorites grid, header link), `components/map/` (list/map toggle, map view, Leaflet map), `components/gallery/` (listing image, gallery, photo viewer, illustrated scenes), `components/listing-draft/` (draft form steps and preview), `components/ui/styles.ts` (shared button, field, card and container classes). Components may import from `lib/`, never the reverse.
- `tests/` mirrors `lib/` (for example `tests/lib/pricing/` tests `lib/pricing/`).
- The `@/` import alias points to the project root, in both `tsconfig.json` and `vitest.config.ts`. Example: `@/lib/pricing/price-per-sqm`.
- `lib/properties/` holds the data model (`Property` is the physical thing, `Listing` is an offer for it) and demo data. Prices and areas are never converted between currencies.
